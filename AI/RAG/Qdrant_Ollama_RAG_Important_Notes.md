# Qdrant + Ollama + RAG — Important Notes

## 1. Basic RAG Flow

User Question
→ Embedding Vector
→ Qdrant Vector Search
→ Relevant Chunks / Payload
→ LLM
→ Human-readable Answer

Qdrant does not generate the answer. It searches information previously stored in it.

## 2. Ollama

Ollama is a local AI model runtime/server.

Example:
Ollama → nomic-embed-text → embedding → 768 numbers

Local API: `http://localhost:11434`

Example request:
```json
{
  "model": "nomic-embed-text",
  "prompt": "Customer Rahul lives in Delhi"
}
```

## 3. Vector

A vector is the numeric representation generated by the embedding model.

Example:
`[0.12, -0.43, 0.81, ...]`

The vector is mainly used for similarity search.

## 4. Qdrant

Qdrant is a vector database.

Local Qdrant:
`http://localhost:6333`

It stores vectors with associated payloads and searches for similar vectors.

## 5. Collection vs Point

Think of Qdrant similarly to SQL Server:

| Qdrant | SQL Server |
|---|---|
| Collection | Table |
| Point | Row |
| Vector | Embedding/vector data |
| Payload | Associated data/metadata |

A collection name is not fixed. You can use names such as:
- `rag_documents`
- `MyCollection`
- `crm_documents`
- `customer_knowledge`

## 6. Creating a Collection

Qdrant collection creation uses `PUT`, not `POST`.

```powershell
$body = @{
    vectors = @{
        size = 768
        distance = "Cosine"
    }
} | ConvertTo-Json -Depth 3

Invoke-RestMethod `
    -Method Put `
    -Uri "http://localhost:6333/collections/rag_documents" `
    -ContentType "application/json" `
    -Body $body
```

`768` = vector dimension in this setup.
`Cosine` = similarity/distance method.

## 7. Checking Collections

`http://localhost:6333/collections`

shows collection names only. It does not show the stored points.

## 8. Checking Collection Information

`http://localhost:6333/collections/rag_documents`

Important fields:
- `points_count`
- vector size
- distance
- status

`points_count: 5` means five Qdrant points are stored.

## 9. Checking Actual Stored Points

Use the scroll API:

```powershell
$body = @{
    limit = 10
    with_payload = $true
    with_vector = $false
} | ConvertTo-Json

Invoke-RestMethod `
    -Method Post `
    -Uri "http://localhost:6333/collections/rag_documents/points/scroll" `
    -ContentType "application/json" `
    -Body $body
```

`with_vector = false` avoids printing all 768 vector numbers.

## 10. Vector vs Payload

Vector:
- Used mainly to find similar information.
- Example: `[0.12, -0.43, 0.81, ...]`

Payload:
- Actual text and metadata associated with the vector.

Example:
```json
{
  "text": "Rahul lives in Delhi.",
  "source": "customer.md",
  "chunkIndex": 0
}
```

Easy rule:
`Vector → Which information is relevant?`
`Payload → What is that information?`

The payload text is normally sent to the LLM as retrieved context.

## 11. One Markdown File Can Create Multiple Points

One `.md` file does not necessarily equal one Qdrant point.

Typical process:

`.md file → chunks → embeddings → Qdrant points`

Example:
```text
customer.md
  ↓
Chunk 1 → Point 1
Chunk 2 → Point 2
Chunk 3 → Point 3
Chunk 4 → Point 4
```

Chunking lets RAG retrieve only the relevant part of a large document.

## 12. `/api/rag/index` vs `/api/rag/ask`

`/api/rag/index` normally performs ingestion/indexing:
`.md → read → chunk → embedding → Qdrant`

Whether it indexes all `.md` files depends on the endpoint implementation.

`/api/rag/ask` normally performs:
`question → embedding → Qdrant search → retrieve chunks → build context → LLM → answer`

## 13. Qdrant Search Code

```csharp
var request = new
{
    query = vector,
    limit,
    with_payload = true
};

var response = await _http.PostAsJsonAsync(
    $"collections/{Collection}/points/query",
    request);

response.EnsureSuccessStatusCode();

var result =
    await response.Content.ReadFromJsonAsync<QdrantSearchResponse>();
```

Meaning:
1. `query = vector` sends the question embedding.
2. `limit = 5` requests up to five results.
3. `with_payload = true` returns payload with the result.
4. `PostAsJsonAsync` sends the request to Qdrant.
5. `EnsureSuccessStatusCode` checks for HTTP errors.
6. `ReadFromJsonAsync` converts JSON into C# objects.

## 14. Qdrant Search Response DTO

The response encountered in this setup was:

```json
{
  "result": {
    "points": []
  },
  "status": "ok"
}
```

Therefore the DTO needs this structure:

```csharp
public class QdrantSearchResponse
{
    public QdrantSearchResult? Result { get; set; }
}

public class QdrantSearchResult
{
    public List<QdrantResult> Points { get; set; } = [];
}
```

The earlier JSON exception occurred because the DTO expected `result` to directly be a list, while Qdrant returned `result.points`.

## 15. Empty Search Result

```json
{
  "result": {
    "points": []
  },
  "status": "ok"
}
```

means the search request succeeded but no matching points were returned.

## 16. Clearing Qdrant Data

You can:
- Delete points while keeping the collection.
- Delete the entire collection.

Deleting the collection removes the collection and its stored points/configuration.

For development/re-indexing, deleting points while keeping the collection is usually convenient.

## 17. Managing Multiple Projects

Separate collections are simple:

```text
Qdrant
├── crm_documents
├── hr_documents
├── dms_documents
└── project4_documents
```

Another option is one collection with a project field in payload:

```json
{
  "project": "CRM",
  "text": "Rahul lives in Delhi."
}
```

Then filter searches by project.

## 18. OKF/Markdown vs RAG

Static Markdown/controlled knowledge:
`Question → Knowledge → LLM`

RAG:
`Question → Embedding → Vector Search → Relevant Chunks → LLM`

RAG is not automatically more accurate.

OKF/static knowledge is useful for:
- Small fixed knowledge
- Controlled instructions
- Business rules
- Definitions

RAG is useful for:
- Large document collections
- Semantic search
- Many documents
- Frequently changing documents
- Retrieving relevant document sections

Live transactional CRM data should normally come from SQL/database access rather than stale document vectors.

## 19. Difficulty: OKF-only vs RAG

OKF-only: easier. Manage knowledge files, structure, and prompts.

RAG + Qdrant: medium difficulty. Manage:
- ingestion
- chunking
- embeddings
- vector dimensions
- Qdrant
- indexing/re-indexing
- metadata/payload
- retrieval quality
- similarity thresholds
- LLM context

A production assistant can combine static knowledge + RAG + SQL.

## 20. One Ollama + Qdrant Server for Multiple APIs

Yes.

```text
AI Infrastructure Server
├── Ollama :11434
└── Qdrant :6333
       ↑
       ├── API 1
       ├── API 2
       └── API 10
```

You do not need to install Ollama and Qdrant on every API server.

For production, secure these services with appropriate private networking, firewall, VPN, reverse proxy, and/or authentication.

## 21. Is Ollama + Qdrant Free Locally?

For self-hosted/open-source use:
- Qdrant open-source server: no per-project license fee.
- Ollama software: free to run locally.
- Local models: no hosted API request fee.
- Server infrastructure is still a cost if you use paid hardware/cloud.

Possible costs:
- CPU/GPU
- RAM
- SSD/storage
- network
- backups
- administration

Check the license of the specific model before commercial production use.

## 23. Core Mental Model

```text
Ollama
  → creates embeddings / runs local models

Embedding
  → converts text meaning into numbers

Vector
  → numeric representation used for similarity

Qdrant
  → stores/searches vectors

Payload
  → stores useful text and metadata

LLM
  → turns retrieved information into a human-readable answer
```

Complete RAG pipeline:

```text
Document
   ↓
Chunk
   ↓
Ollama
   ↓
Vector
   ↓
Qdrant
   ↓
Search
   ↓
Payload / relevant chunks
   ↓
LLM
   ↓
Answer
```
